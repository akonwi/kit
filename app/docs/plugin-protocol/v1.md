# Kit external plugin protocol v1

## Status and terminology

This document is the normative specification for Kit external plugin protocol
version 1. The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**,
**SHOULD NOT**, and **MAY** are to be interpreted as described by RFC 2119.

The protocol uses JSON-RPC 2.0. JSON-RPC defines message envelopes, request ids,
responses, errors, notifications, and batches. This document defines the stdio
transport profile, process lifecycle, methods, payloads, limits, and application
semantics required by Kit plugins.

In examples:

- **Kit request** means Kit sends a JSON-RPC request handled by the plugin.
- **Plugin request** means the plugin sends a JSON-RPC request handled by Kit.
- **Kit notification** and **plugin notification** have the corresponding
  direction and omit a JSON-RPC `id`.

All protocol-owned method names use the `kit/` prefix regardless of direction.
The lifecycle methods `initialize` and `shutdown` are unprefixed. Method and
property names are case-sensitive. Names beginning with `rpc.` are reserved by
JSON-RPC and MUST NOT be used by Kit or plugins.

Protocol methods use named object params. A method described as having no
params MUST omit the `params` member; `"params": null` is not valid. Unknown
methods still follow standard JSON-RPC method-not-found and notification
handling.

## Discovery and manifest

Kit discovers manifests from these locations in order:

1. `~/.kit/plugins/*/plugin.json`
2. `<cwd>/.kit/plugins/*/plugin.json`

Each `*` is one immediate child directory. Discovery is not recursively deeper
than that child. Kit SHOULD follow a child symlink that resolves to a directory.
A standalone plugin repository may therefore put `plugin.json` at its root and
be cloned or symlinked into a plugin directory.

Within each scope, Kit sorts installations by child directory name. It validates
all discovered manifests and resolves duplicate plugin ids before launching
processes. The first manifest in discovery order owns an id. A later duplicate
MUST NOT launch, and Kit MUST show a persistent error toast requiring manual
dismissal that identifies both manifest paths.

The v1 manifest is defined by `manifest.schema.json`:

```json
{
  "$schema": "https://raw.githubusercontent.com/akonwi/kit/main/app/docs/plugin-protocol/manifest.schema.json",
  "manifestVersion": 1,
  "id": "speech",
  "name": "Speech",
  "transport": {
    "type": "stdio",
    "command": "python3",
    "args": ["-u", "plugin.py"]
  }
}
```

`name` and `transport.args` are optional. Stdio is the only valid v1 transport.
Plugin ids MUST:

- match `^[a-z][a-z0-9-]*$`
- contain at most 32 characters
- not equal `kit`
- not begin with `kit-`
- not collide with a Kit-reserved top-level command domain

The child directory name is an installation label and does not define plugin
identity.

Kit launches the command without a shell. A bare command is resolved through
`PATH`. A command containing a path is resolved relative to the manifest
directory. Arguments are passed literally without shell expansion, globbing,
tilde expansion, or environment interpolation. The process cwd is the manifest
directory. The process inherits Kit's environment.

Kit does not install plugin dependencies. The declared command MUST already be
runnable in the user's environment.

## Trust model

User and project plugins launch automatically. A plugin process runs as the
same OS user as Kit and is not sandboxed. It may access the filesystem,
environment, network, and subprocesses available to that user. The JSON-RPC
boundary protects Kit's internal object graph and isolates process lifecycle;
it is not a security boundary around the user's machine.

Users MUST only install or open projects containing plugins they trust.

## Stdio transport and framing

Kit writes JSON-RPC messages to the plugin's stdin and reads JSON-RPC messages
from the plugin's stdout. The plugin MUST write human-readable logs and
diagnostics to stderr. It MUST NOT write non-protocol content to stdout.

The stream encoding is UTF-8. Each complete JSON-RPC message is encoded as one
line terminated by `\n`. Readers MUST also accept `\r\n`. Newlines inside JSON
strings are escaped and do not delimit frames. Readers MUST ignore empty lines.
Writers MUST serialize outbound frames so concurrent handlers cannot interleave
bytes.

A frame may contain one JSON-RPC object or one standard JSON-RPC batch array.
Batch processing and responses follow JSON-RPC 2.0. Neither endpoint is
required to use batches, but both MUST accept valid batches.

The maximum encoded frame size is 16 MiB. An endpoint MUST reject an oversized
outbound frame before writing it. If Kit receives more than 16 MiB before a
frame delimiter, it MUST terminate the plugin and report a persistent protocol
error. The limit includes base64 tool-result image data.

Malformed JSON or non-protocol stdout fails initialization if the plugin is not
ready. After initialization it terminates the plugin, removes its contributions,
and produces a persistent protocol-error toast requiring manual dismissal. Kit
MAY include a safely truncated offending line in diagnostics.

Kit maintains an independent serialized write queue for each plugin and MUST
honor normal pipe backpressure. One slow plugin MUST NOT block Kit or another
plugin. The maximum queued outbound data for one plugin is 32 MiB. Exceeding the
limit marks the plugin unresponsive and terminates it.

Kit permits at most 128 concurrently pending plugin-to-Kit requests per plugin.
Additional requests receive error `-32006` until existing requests settle.
Notifications do not count toward this limit. Kit MAY terminate a plugin that
floods notifications and prevents fair processing.

## Lifecycle

### Initialization

Kit initializes plugins sequentially in deterministic discovery order. A
failure does not prevent later plugins from initializing.

The first request from Kit is `initialize`:

```json
{
  "jsonrpc": "2.0",
  "id": "kit-1",
  "method": "initialize",
  "params": {
    "protocolVersion": 1,
    "context": {
      "project": {
        "cwd": "/project",
        "git": {
          "root": "/project",
          "branch": "main",
          "dirty": true
        }
      },
      "session": {
        "id": "f22fd759-87d0-4480-9545-bca60b7c9cda",
        "name": "Plugin protocol"
      }
    }
  }
}
```

`project.cwd` and Git `root` paths are absolute. `project.git` is `null` when
the cwd is not inside a Git worktree. Git `branch` is nullable for a worktree
without a named branch. `session.name` is nullable.

The plugin accepts v1 by returning:

```json
{
  "jsonrpc": "2.0",
  "id": "kit-1",
  "result": {
    "protocolVersion": 1
  }
}
```

A plugin that does not support v1 MUST reject initialization with an
application error. There is no version range or optional capability negotiation
in v1.

The plugin MUST NOT send requests or notifications other than responses and
stderr diagnostics before initialization succeeds. Kit considers the plugin
ready when it receives the successful response. Kit allows ten seconds for the
response; timeout, early exit, rejection, or malformed output fails
initialization, terminates the process, and produces a persistent failure toast.

### Shutdown

Kit removes a plugin's contributions as soon as shutdown begins, rejects new
plugin requests with `-32002`, cancels outstanding requests, and sends:

```json
{
  "jsonrpc": "2.0",
  "id": "kit-99",
  "method": "shutdown"
}
```

The plugin SHOULD stop background work, release resources, and return `null`:

```json
{
  "jsonrpc": "2.0",
  "id": "kit-99",
  "result": null
}
```

The plugin SHOULD then exit. Kit permits two seconds for graceful shutdown,
then sends `SIGTERM` and uses `SIGKILL` if the process still does not exit.

Kit does not show a failure toast for an exit initiated by app shutdown,
`/reload`, or project replacement. Any unrequested exit after initialization is
a crash, including exit code zero. Kit removes contributions immediately,
fails pending operations with a plugin-unavailable error, and shows a persistent
failure toast. Kit does not automatically restart crashed plugins in v1.

### Scope and reload

User plugins persist across session switches and project cwd changes. They
receive context events. Project plugins persist across session switches that
retain the same cwd, but Kit shuts them down before leaving their discovery cwd
and discovers new project plugins after retargeting.

On a cwd change Kit:

1. stops old project plugins
2. updates active project context
3. notifies persistent user plugins with `kit/events/project.changed`
4. discovers and initializes new project plugins

`/reload` stops project plugins and then user plugins in reverse initialization
order. It then rediscovers and initializes user plugins followed by project
plugins in normal order. V1 does not reuse processes or send a hot-reload
message.

## Concurrency and request ids

The connection is full-duplex. Both endpoints MUST continue reading frames
while handlers are pending. Requests may execute concurrently, responses may
arrive in any order, and nested requests are valid in either direction.

Request ids MUST be strings or integers and MUST be unique among that sender's
outstanding requests. Request-id namespaces are independent in each direction.
Fractional numeric ids and null request ids are not allowed by this protocol.

Frames and event notifications are dispatched in wire order, but handler
completion order is not guaranteed. Writers MUST serialize outbound frames.
Tool execution observes each tool's declared execution mode. Interceptors run
sequentially for one tool call, while separate tool calls may cause concurrent
interceptor requests.

## Cancellation

JSON-RPC does not define cancellation. Either endpoint cancels an outstanding
request it sent using this notification:

```json
{
  "jsonrpc": "2.0",
  "method": "kit/cancel",
  "params": {
    "id": "kit-30"
  }
}
```

Cancellation is best-effort. Cancelling an unknown or completed request is
ignored. If cancellation wins the completion race, the original request returns:

```json
{
  "jsonrpc": "2.0",
  "id": "kit-30",
  "error": {
    "code": -32001,
    "message": "Request cancelled"
  }
}
```

Notifications cannot be cancelled. Disconnecting cancels all outstanding
requests in both directions. A plugin is responsible for propagating
cancellation to nested requests it initiated; the wire protocol does not carry
parent request ids.

Kit does not impose a general timeout on commands, tools, interceptors, or
interactive UI. Initialization and shutdown use their explicit lifecycle
timeouts.

## Identity and contribution ids

Commands, tools, header/footer items, and subagents are owned by plugin id and
local contribution id. Local command and contribution ids use dot-separated
lowercase kebab-case segments. Kit prefixes the manifest plugin id to derive a
canonical id. Command pickers present the local id while retaining the canonical
id for ownership, keybindings, and invocation.

Plugin `speech` registering local command `settings.open` owns
`speech.settings.open`. The plugin always receives its local id in invocation
requests. Canonical ids are used in user settings and intentional cross-owner
operations.

Tool local ids use lowercase snake case. Kit exposes canonical tool
`speech.speak_text` to models as `speech__speak_text`. The final model-facing
name MUST satisfy provider naming constraints and contain at most 64 characters.
Kit rejects `kit/tools/register` with `-32602` when the derived model-facing
name would exceed that limit.

Ids are unique within each contribution type. Explicit removal uses the local
id and is idempotent. There are no callback handler ids or registration tokens.
All remaining contributions and hide claims are removed on disconnect.

## Commands

### `kit/commands/register` — plugin request

```json
{
  "jsonrpc": "2.0",
  "id": "plugin-1",
  "method": "kit/commands/register",
  "params": {
    "id": "toggle",
    "description": "Toggle spoken responses",
    "argName": null,
    "category": "Speech"
  }
}
```

`id` and a non-empty `description` are required. `argName` and `category` are
optional or nullable. Kit returns the canonical id:

```json
{
  "jsonrpc": "2.0",
  "id": "plugin-1",
  "result": {
    "id": "speech.toggle"
  }
}
```

The slash command is presented as `/toggle` with `speech` shown as searchable
owner metadata; `speech.toggle` remains its canonical id for keybinding settings
and internal invocation. Different plugins may present the same local command
name because their canonical ids remain distinct. The picker retains the selected canonical identity when invoking an
otherwise identical local name. A duplicate local id within the same plugin
returns `-32003`.

### `kit/commands/execute` — Kit request

```json
{
  "jsonrpc": "2.0",
  "id": "kit-7",
  "method": "kit/commands/execute",
  "params": {
    "id": "toggle",
    "args": "optional command arguments"
  }
}
```

The plugin returns `null` on success. A plugin error becomes a command-failure
toast in Kit. The request is cancellable. `args` is the empty string when the
user invokes the command without arguments.

### `kit/commands/unregister` — plugin request

The plugin sends `{ "id": "toggle" }`. Kit returns `null`. Removing an
unknown id is successful and has no effect.

## Tools

### Kit Tool Schema Profile v1

Tool `inputSchema` values are based on JSON Schema Draft 2020-12. The root MUST
be an object schema. `$schema` is optional; when present it MUST equal
`https://json-schema.org/draft/2020-12/schema`.

V1 supports these keywords:

- `type`
- `description`
- `properties`
- `required`
- `additionalProperties` as a boolean
- `items`
- `enum`
- `const`
- `anyOf`
- `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`
- `minLength`, `maxLength`, `pattern`
- `minItems`, `maxItems`

Supported primitive types are `object`, `array`, `string`, `number`, `integer`,
`boolean`, and `null`. Nullable values use `anyOf`.

V1 rejects `$ref`, `$defs`, `allOf`, `oneOf`, `not`, conditionals,
`dependentSchemas`, `unevaluatedProperties`, `format`, `contentEncoding`, and
external references. Kit validates the schema at registration and returns
`-32602` for invalid or unsupported schemas.

Kit validates model-produced input before invoking the plugin. It does not
coerce values, insert defaults, remove unknown properties, or execute argument
preparation callbacks. The plugin receives the validated JSON object exactly.

### `kit/tools/register` — plugin request

```json
{
  "jsonrpc": "2.0",
  "id": "plugin-3",
  "method": "kit/tools/register",
  "params": {
    "id": "speak",
    "label": "Speak",
    "description": "Speak text aloud",
    "inputSchema": {
      "type": "object",
      "properties": {
        "text": {
          "type": "string"
        }
      },
      "required": ["text"],
      "additionalProperties": false
    },
    "executionMode": "sequential",
    "promptSnippet": null,
    "promptGuidelines": []
  }
}
```

`id`, `description`, and `inputSchema` are required. `label` defaults to the
local id. `executionMode` is `sequential` or `parallel` and defaults to
`sequential`. Prompt fields are optional. Kit returns:

```json
{
  "jsonrpc": "2.0",
  "id": "plugin-3",
  "result": {
    "id": "speech.speak",
    "modelName": "speech__speak"
  }
}
```

There is no streaming tool-progress method in v1.

### `kit/tools/execute` — Kit request

```json
{
  "jsonrpc": "2.0",
  "id": "kit-24",
  "method": "kit/tools/execute",
  "params": {
    "id": "speak",
    "toolCallId": "call-42",
    "input": {
      "text": "Done"
    }
  }
}
```

The result contains `content`, optional JSON `details`, and optional
`terminate`:

```json
{
  "jsonrpc": "2.0",
  "id": "kit-24",
  "result": {
    "content": [
      {
        "type": "text",
        "text": "Spoke the requested text."
      }
    ],
    "details": null,
    "terminate": false
  }
}
```

Content is either text or a base64 image:

```json
{
  "type": "image",
  "data": "<base64>",
  "mimeType": "image/png"
}
```

`details` may contain any JSON value. `terminate` defaults to false. Execution
is cancellable. An execution failure may use application error `-32000`.

### `kit/tools/unregister` — plugin request

The plugin sends its local tool id. Removal is idempotent and returns `null`.

## Tool-call interception

A plugin may own one tool-call interceptor. It opts in with the idempotent
plugin request `kit/tool-calls/register-interceptor` and opts out with
`kit/tool-calls/unregister-interceptor`. Both have no params and return `null`.

Before a tool executes, Kit calls each registered interceptor sequentially in
registration order:

```json
{
  "jsonrpc": "2.0",
  "id": "kit-30",
  "method": "kit/tool-calls/before-execute",
  "params": {
    "toolCall": {
      "id": "call-42",
      "name": "bash",
      "input": {
        "command": "npm publish"
      }
    }
  }
}
```

The plugin returns one of:

```json
{ "action": "allow" }
```

```json
{
  "action": "reject-and-continue",
  "message": "The user rejected this command."
}
```

`allow` continues to later interceptors. The first rejection blocks the tool.
All core and plugin-contributed tools are eligible. An interceptor RPC error,
malformed response, process exit, or cancellation failure fails closed and
blocks the tool. `toolCall.name` is the exact model-facing tool name, including
the `plugin__tool` form for plugin tools. An interceptor may make nested UI
requests. Approval policies should use `kit/ui/confirm`; web mode routes that
confirmation through the same reconnect-safe, first-response-wins interaction
broker as other remote input. Cancelling the interceptor request must propagate
to any nested confirmation so stale approval dialogs close.

## UI

### `kit/ui/toast` — plugin notification

```json
{
  "jsonrpc": "2.0",
  "method": "kit/ui/toast",
  "params": {
    "title": "Speech enabled",
    "subtitle": null,
    "variant": "info",
    "persistent": false
  }
}
```

`variant` is `info`, `warning`, or `error`. Subtitle is optional or nullable;
`persistent` defaults to false. In web mode Kit forwards the notification as a
sequenced `ui.toast.requested` event so connected and resumable browser clients
can present the same toast semantics as the TUI.

### `kit/ui/confirm` — plugin request

Params contain required `title`; optional or nullable `message`, `confirmLabel`,
and `cancelLabel`; and optional boolean `defaultValue`. `message` is rendered as
Markdown, including fenced code blocks. The result is a boolean; cancel and Escape
return false. The request is cancellable.

### `kit/ui/input` — plugin request

Params contain required `title` and optional or nullable `message`,
`placeholder`, and `initialValue`. The result is a string or null when
cancelled. The request is cancellable.

### `kit/ui/select` — plugin request

Options use one normalized shape:

```json
{
  "jsonrpc": "2.0",
  "id": "plugin-12",
  "method": "kit/ui/select",
  "params": {
    "title": "Choose target",
    "message": null,
    "options": [
      {
        "label": "Current file",
        "value": "file",
        "description": "Use the active file"
      },
      {
        "label": "Whole project",
        "value": "project",
        "description": null
      }
    ],
    "filterable": true,
    "placeholder": "Filter targets"
  }
}
```

Option values may be any JSON value. Selection returns `{ "value": ... }` so
JSON null remains a selectable value. Cancellation returns null. The request is
cancellable. `filterable` defaults to false.

V1 has no theme query, theme-change event, or `ui.text` method.

## Header and footer contributions

Plugins manage owned items with `kit/header/set`, `kit/header/clear`,
`kit/footer/set`, and `kit/footer/clear`. `set` is a plugin request with local
`id`, normalized `content` segments, optional `side`, and optional `clickable`:

```json
{
  "jsonrpc": "2.0",
  "id": "plugin-20",
  "method": "kit/header/set",
  "params": {
    "id": "status",
    "content": [
      {
        "text": "speech "
      },
      {
        "text": "on",
        "style": {
          "fg": "toolText",
          "bold": true
        }
      }
    ],
    "side": "right",
    "clickable": true
  }
}
```

`side` defaults to `right`; `clickable` defaults to false. `set` creates or
updates the same item without changing its order and returns the canonical id.
`clear` receives a local id, removes the caller's item, and is idempotent.

Style `fg` and `bg` values are documented public Kit theme token names, not
literal colors. Kit resolves tokens at render time, so contributions track
theme changes without receiving theme values. V1 styles also support `bold`,
`dim`, `italic`, `underline`, and `strikethrough`. The `ThemeToken` enum in
`protocol.schema.json` is the normative list of allowed token names.

When a clickable item is activated, Kit sends `kit/header/click` or
`kit/footer/click` to the owner with the local id. The plugin returns `null`.
Click requests are cancellable.

Plugins intentionally suppress canonical items with `kit/header/hide`,
`kit/header/show`, `kit/footer/hide`, and `kit/footer/show`. A hide request is
idempotent per plugin and target. Show removes only that plugin's hide claim. An
item remains hidden while any plugin owns a claim. Disconnecting clears all
owned hide claims.

Kit exposes these stable built-in chrome ids for intentional suppression:

- `kit.header.title`
- `kit.header.model`
- `kit.header.update`
- `kit.footer.location`

## Subagents

`kit/subagents/register` is a plugin request with local `id`, non-empty
`description`, non-empty `instructions`, and optional or nullable Kit model id:

```json
{
  "jsonrpc": "2.0",
  "id": "plugin-30",
  "method": "kit/subagents/register",
  "params": {
    "id": "reviewer",
    "description": "Review code changes for regressions",
    "instructions": "Inspect the relevant changes and return concrete findings.",
    "model": null
  }
}
```

Kit returns the canonical id, which is the name exposed to the agent. Kit owns
execution; there is no plugin subagent execute method. Registration conflicts
with built-in, file-discovered, or plugin subagents return `-32003`.

`kit/subagents/unregister` removes the local id idempotently and returns null.

## System-prompt contribution

Each plugin owns one system-prompt slot. `kit/system-prompt/set` takes non-empty
`text`, creates or replaces the slot, preserves plugin load ordering, and
returns null. A plugin with multiple policy sections combines them in that
string. `kit/system-prompt/clear` has no params, is idempotent, and returns null.

Changes apply to subsequent model requests. Disconnecting removes the slot.

## Session submission

The only external session mutation is `kit/session/submit-message`:

```json
{
  "jsonrpc": "2.0",
  "id": "plugin-51",
  "method": "kit/session/submit-message",
  "params": {
    "sessionId": "f22fd759-87d0-4480-9545-bca60b7c9cda",
    "text": "Review the current working tree."
  }
}
```

V1 accepts text only. Kit rejects empty text with `-32602` and rejects a stale
session id with `-32004`. If the agent is idle, submission starts a turn. If it
is running, submission queues a follow-up. The request is cancellable and
returns null on success.

There are no external methods to rename sessions, read transcripts, submit
Kit-specific synthetic prompt-command messages, or retarget cwd.

## Opening URLs

`kit/system/open-url` is a plugin request with one `url`. V1 accepts only
absolute HTTP and HTTPS URLs. Kit invokes the platform opener and returns null
on success or an RPC error on failure.

Plugin diagnostics use stderr; there is no RPC log method.

## Successful results

The response `result` for each successful request MUST validate against the
named definition in `protocol.schema.json` shown below. The endpoint validates
the response according to the method associated with the pending request id.

| Request method | Result definition |
| --- | --- |
| `initialize` | `InitializeResult` |
| `kit/commands/register`, `kit/header/set`, `kit/footer/set`, `kit/subagents/register` | `CanonicalIdResult` |
| `kit/tools/register` | `ToolRegisterResult` |
| `kit/tools/execute` | `ToolExecuteResult` |
| `kit/tool-calls/before-execute` | `ToolCallDecision` |
| `kit/ui/confirm` | `ConfirmResult` |
| `kit/ui/input` | `InputResult` |
| `kit/ui/select` | `SelectResult` |
| All other request methods | `NullResult` |

## Events

Kit sends every public event to every ready plugin as a notification. Plugins
do not subscribe. A plugin handles the event method or ignores it. Event
notifications are dispatched in wire order and never wait for plugin
acknowledgment.

### `kit/events/project.changed`

Sent to persistent user plugins when active cwd changes. Params use the same
project shape as initialization: absolute `cwd` and nullable Git context.

### `kit/events/git.changed`

Params are `{ "git": <Git context> }`, or `{ "git": null }` after leaving a
Git worktree. The wrapper keeps JSON-RPC `params` as a structured value.

### `kit/events/session.changed`

Params use the same `{ "id", "name" }` session shape as initialization. This
covers active-session switches and name changes.

### `kit/events/agent.turn.started`

```json
{
  "jsonrpc": "2.0",
  "method": "kit/events/agent.turn.started",
  "params": {
    "sessionId": "f22fd759-87d0-4480-9545-bca60b7c9cda",
    "turnId": "turn-42"
  }
}
```

Sent once when Kit creates a turn, before model and tool activity begins.

### `kit/events/agent.turn.completed`

```json
{
  "jsonrpc": "2.0",
  "method": "kit/events/agent.turn.completed",
  "params": {
    "sessionId": "f22fd759-87d0-4480-9545-bca60b7c9cda",
    "turn": {
      "id": "turn-42",
      "messages": [
        {
          "role": "user",
          "content": [
            {
              "type": "text",
              "text": "Explain the plugin system."
            }
          ]
        },
        {
          "role": "assistant",
          "content": [
            {
              "type": "text",
              "text": "The plugin system uses JSON-RPC over stdio."
            }
          ]
        }
      ]
    }
  }
}
```

V1 public turn messages include ordered user and assistant messages with text
content only. Kit omits provider metadata, usage, thinking, tool calls, tool
results, bash transcript entries, synthetic metadata, image data, timestamps,
and persistence fields. Multipart user messages retain only textual portions.

V1 has no runtime wildcard event, streaming deltas, tool lifecycle events,
retry or compaction events, settings or model events, bash events, or
persistence events.

## Errors

Kit and plugins use standard JSON-RPC errors when applicable:

| Code | Meaning |
| ---: | --- |
| `-32700` | Parse error |
| `-32600` | Invalid request |
| `-32601` | Method not found |
| `-32602` | Invalid params |
| `-32603` | Internal error |

Kit defines these implementation errors:

| Code | Meaning |
| ---: | --- |
| `-32001` | Request cancelled |
| `-32002` | Endpoint not ready or shutting down |
| `-32003` | Contribution conflict |
| `-32004` | Active session changed |
| `-32005` | Protocol or application limit exceeded |
| `-32006` | Temporarily busy |

Error `message` MUST be concise and safe to display. Optional `data` MUST be a
JSON value and SHOULD contain structured details such as contribution type and
canonical id. Stack traces MUST NOT be sent over RPC; they belong on stderr.

A plugin may return `-32000` for an execution failure with no more specific
protocol meaning. Kit preserves plugin command and tool error messages for user
feedback subject to a safe display-length limit.

Error `-32005` is used only when an endpoint can safely report a limit violation
as a response. Transport-level violations that prevent a valid response follow
the fatal process policy described under framing.

Unknown requests return `-32601`. Per JSON-RPC, unknown notifications receive
no response. Malformed stdout triggers parse or invalid-request handling when
possible and then follows the strict process-failure policy.

## Diagnostics

Kit continuously drains stderr and retains a 64 KiB in-memory tail per plugin.
Older diagnostic bytes are discarded. Ordinary stderr output does not create a
toast.

Persistent manually dismissed failure toasts identify the plugin id, manifest
path, failure phase, exit code or signal when available, and a concise final
stderr line when available. Routine request errors are returned through
JSON-RPC or operation-specific UI and do not create persistent plugin-failure
toasts.

## Conformance

A conforming plugin MUST:

- satisfy `manifest.schema.json`
- implement JSON-RPC 2.0 request, response, notification, error, and batch
  processing used by this protocol
- implement the newline-delimited stdio framing and limits in this document
- reserve stdout for protocol frames and stderr for diagnostics
- complete initialization before invoking Kit methods
- continue reading while handlers are pending
- dispatch Kit requests by local contribution id
- honor cancellation and shutdown
- return only JSON values defined by this protocol

Kit's conformance suite SHOULD include a dependency-free Python plugin process
that exercises initialization, commands, tools, interception, events, nested UI
requests, cancellation, and graceful shutdown without importing a Kit SDK.
