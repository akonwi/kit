# Developing the Kit plugin protocol

Plugins speak a versioned JSON-RPC protocol with Kit over stdio. A change to
it is complete only when the Go records, the host, the generated schemas, the
specification, the fixtures, and the tests agree.

This guide is procedural. The decisions behind it are in
[ADR 0065](adrs/0065-stabilize-the-plugin-protocol-as-version-2.md), and the
protocol itself is specified in
[docs/plugin-protocol/v2.md](plugin-protocol/v2.md). Session API changes follow
[docs/api-development.md](api-development.md) instead; plugins are not session
API clients.

## Ownership

| Concern | Owner |
| --- | --- |
| Wire records, method catalogue, error codes and reasons | `api/pluginprotocol` |
| Committed schemas | `docs/plugin-protocol/v2/*.schema.json`, generated by `api/pluginprotocol/cmd/emit` |
| Normative specification | `docs/plugin-protocol/v2.md` |
| Host behavior, bounds, and strict member lists | `internal/plugin` (`protocol_members.go` derives member lists from the records) |
| Wiring into sessions and clients | `internal/server` |
| Example and conformance plugins | `.kit/plugins/*`, `internal/plugin/testdata` |
| TypeScript helper and its in-memory Kit | `sdk/plugin` (its protocol types are generated by `cmd/emit`) |

Host types alias the `api/pluginprotocol` records where shapes coincide. Do not
declare a second Go record for a wire shape, and do not hand-edit the generated
schemas.

## Compatibility

Every change is either compatible within the current version or needs a new
one. Within version 2, Kit may:

- add optional members to objects it sends;
- add notifications it sends;
- add plugin-to-Kit methods, and optional members to their params.

Everything else is breaking: removing or renaming a method or member, adding a
required member, tightening a shape or bound, changing a result, an error code,
or a reason's meaning, and adding a Kit-to-plugin request (an older plugin
would answer it with an error). A breaking change needs a new protocol
version, with an ADR, its own `docs/plugin-protocol/vN.md`, and its own
`docs/plugin-protocol/vN/` schemas; the previous version stays supported until
an explicit removal.

Objects Kit sends are open in the schema and objects plugins send are closed.
Keep it that way: plugins rely on ignoring unknown members, and Kit rejects
members it does not know.

## Changing the protocol

1. Decide compatibility as above. If the change is breaking, stop and write the
   ADR first.
2. Add or change the records in `api/pluginprotocol`. Give every member its
   JSON name, `schema:` constraints, and a `doc:` description; document
   exported identifiers. Text a plugin sends takes the host's bound as
   `maxLength` and its character rule as `text=` (see `text.go`), so the
   schema rejects what the host rejects wherever a schema can.
3. Add or change the method in `Methods()` in `methods.go`: direction, params,
   result, declared error codes, and summary. New error reasons go in
   `errors.go`.
4. Regenerate the schemas from the repository root:

   ```sh
   go run ./api/pluginprotocol/cmd/emit
   ```

5. Implement the host in `internal/plugin` through the records. Strict member
   lists in `protocol_members.go` derive from the records, so a member exists
   on the wire exactly when it exists in the type. Enforce byte and count
   bounds in the host, at the boundary where the message arrives, and return
   the declared error codes.
6. Update `docs/plugin-protocol/v2.md`: the method's section, its bounds, and
   its errors. State only what Kit does.
7. Exercise the change in a fixture under `.kit/plugins` when a user would
   reach it, and test it (below).
8. Expose the change in the TypeScript helper: `cmd/emit` regenerates its
   protocol types, and `sdk/plugin/kit-plugin.ts` and
   `sdk/plugin/kit-plugin-testing.ts` need the API and the in-memory Kit's
   answer, with tests in `sdk/plugin/test`.

## Tests

| Check | Where |
| --- | --- |
| Committed schemas match the records | `TestCommittedSchemasAreCurrent` in `api/pluginprotocol` |
| Each method has a valid example; plugin-sent objects are closed and Kit-sent objects open | `api/pluginprotocol/schema_test.go` |
| Every message Kit sends in the version 2 tests validates against the schema | `TestVersion2MessagesKitSendsMatchTheSchema` in `internal/plugin` |
| Every message each version 2 fixture writes validates against the schema, and the fixtures together send every plugin method | `TestVersion2FixturesConformToTheSchema` in `internal/plugin` |
| The host and the schema accept and reject the same representative text and addresses | `TestSchemaAndHostAgreeOnPluginText` in `internal/plugin` |
| Removed methods and members fail with their exact error and the endpoint keeps serving | `TestVersion2RejectsPrunedSurfaceAndKeepsServing` in `internal/plugin` |
| Behavior through a real subprocess and session | `internal/plugin` and `internal/server` tests |

New behavior needs a test asserting the exact result or error, including the
error's `data.reason` when it has one. A new rejection needs a test that the
host keeps serving afterwards.

## Validation

```sh
gofmt -l .
go build ./...
go vet ./...
go test ./...
go test -race ./internal/plugin ./api/pluginprotocol ./internal/server
```

For the TypeScript helper, run `bun install` and `bun run check` in
`sdk/plugin`.

`gofmt -l .` must print nothing outside `ard-out/` build output. Fixture tests
need `python3` and `bun` on `PATH`; a fixture whose command is missing is
skipped.
