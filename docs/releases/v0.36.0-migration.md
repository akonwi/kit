# Migrating to Kit 0.36.0

These instructions can be given to a coding assistant. Preserve the user's intent
through supported interfaces, not mechanical renaming. Use source and examples
at **tag v0.36.0**, not remembered TypeScript APIs or a later `main` branch.

## Safety and inventory

Resolve the active home as `${KIT_HOME:-$HOME/.kit}`. Back up configuration and
plugin source. Inventory settings, themes, plugins, MCP servers, skills, prompts,
and agent definitions there and in the project. Do not delete or rewrite legacy
sessions, databases, or credential stores. Native sessions start fresh.

Treat `auth.json`, `mcp-auth.json`, environment values, and extension configuration
as potentially secret. Never paste tokens into prompts or commit them. Use
supported login flows rather than converting credential caches.

Test with a separate `KIT_HOME` **and a trusted fixture project**. An isolated home
does not suppress project plugins, which load automatically as trusted same-user
code. Ask before deleting configuration or running extensions with side effects.

## Settings

The native shared store reads `<Kit home>/settings.json`:

| Field | Supported meaning |
| --- | --- |
| `theme` | Theme name; custom themes live in `<Kit home>/themes/*.json`. Validate against the native theme format. |
| `defaultModel` | Available canonical `provider/model-id`, not a display label. |
| `diffWrapLines` | JSON boolean controlling diff wrapping. |
| `modelOverrides` | Exact model-selector keys, each supporting a positive integer `contextWindow`. Respect actual provider limits. |

Shape example, not a recommendation to change provider or context budget:

```json
{
  "defaultModel": "openai/gpt-4o-mini",
  "diffWrapLines": true,
  "modelOverrides": {
    "openai/gpt-4o-mini": { "contextWindow": 128000 }
  }
}
```

Unknown top-level settings are preserved on write, but **preserved is not active**.
Make a supported/needs-adjustment/unsupported inventory. Do not silently delete
unknown fields or invent equivalents for browser or plugin-specific settings.
Configurable keybindings and legacy keybinding compatibility are excluded.

Themes, MCP, skills, prompts, and subagents have separate schemas/loaders; do not
move them into arbitrary `settings.json` keys. Consult
[`internal/settings/store.go`](../../internal/settings/store.go),
[model overrides](../features/model-overrides.md), and
[themes](../features/themes.md).

## MCP, instructions, skills, and prompts

- MCP sources, lowest to highest priority: `<Kit home>/mcp.json`, project
  `.mcp.json`, project `.agents/mcp.json`. Later scalar values win; environment
  and header maps merge by key. Inspect all sources before changing a server.
- Preserve command/argument, environment-reference, and HTTP/auth intent using
  [`internal/mcpconfig`](../../internal/mcpconfig). Do not inline secrets or
  copy authentication-cache internals. Reauthenticate where needed.
- Merge relevant `CLAUDE.md` instructions into `AGENTS.md` without overwriting
  existing guidance. Kit does not discover `CLAUDE.md`.
- Global skills: `<Kit home>/skills/`. Project skills: `.agents/skills/`.
  Built-ins take priority, then global skills, then project skills; project
  definitions do not override global names.
- Prompt commands: `<Kit home>/prompts/` and project `.agents/prompts/`.
  Follow the [template format](../features/prompt-commands.md), not an old
  executable-plugin convention.
- Reload after changing skills or prompts; a cwd change alone does not refresh
  these registries. Consult [subagents](../features/subagents.md) for agent
  definitions instead of inferring their schema from skills.

## Plugin migration

Install `plugin.json` in `<Kit home>/plugins/<directory>/` or project
`.kit/plugins/<directory>/`. A minimal launch manifest is:

```json
{
  "manifestVersion": 1,
  "id": "my-plugin",
  "name": "My plugin",
  "transport": {
    "type": "stdio",
    "command": "python3",
    "args": ["-u", "plugin.py"]
  }
}
```

Use a unique ID matching `[a-z][a-z0-9-]{0,31}` and avoid reserved Kit command
domains. Unknown manifest fields are rejected. Commands/arguments are literal,
not shell syntax. Install any interpreter the extension requires separately.

1. Replace in-process imports, callbacks, and direct runtime/UI access with
   subprocess JSON-RPC. JavaScript remains an option with an installed runtime.
2. Use newline-delimited JSON-RPC 2.0 on stdin/stdout. Flush messages. Send
   diagnostics to stderr; stdout is protocol-only.
3. Handle `initialize`, return `{ "protocolVersion": 1 }`, read its session/project
   context, then register contributions. Handle `shutdown` and applicable
   `kit/cancel` requests. Cancellation does not roll back external side effects.
4. Match response IDs; distinguish requests, responses, and notifications. Do not
   reply to notifications or treat registration responses as host invocations.
   Support bidirectional requests instead of assuming synchronous one-way calls.
5. Commands: `kit/commands/register` and `kit/commands/execute`. Model tools:
   `kit/tools/register` and `kit/tools/execute`. Validate input and return the
   documented result shape. Start from the working
   [command demo](../../.kit/plugins/plugin-demo) and
   [tool demo](../../.kit/plugins/tool-demo), not guessed payloads.
6. For other capabilities, consult corresponding source/examples for
   `kit/subagents/register`, `kit/tool-calls/register-interceptor`,
   `kit/ui/confirm`, `kit/ui/input`, `kit/ui/select`, `kit/ui/toast`, and footer
   contributions. Similar method names do not imply compatible schemas.
7. Replace direct renderer mutations with supported UI messages. Only bottom-right
   footer chrome is plugin-configurable; header and bottom-left status are owned
   by Kit. Do not import renderer internals to emulate removed widget APIs.
8. Handle applicable `kit/events/project.changed`, `kit/events/session.changed`,
   `kit/events/agent.turn.started`, and `kit/events/agent.turn.completed` payloads.
   Never query Kit's SQLite files as a workaround for a missing public API.

### Lifecycle and policy caveats

An instance belongs to one session and plugin ID, not the entire application.
It can keep running while that loaded session has no attached client. User plugins
survive cwd changes and receive a project-change event; project plugins are
replaced. Reload revokes contributions and cancels requests before replacing
instances. In-memory state is not durable across reload or server restart, and
interrupted side effects are not automatically replayed.

Initialization is asynchronous: early turns may precede registration. A policy
plugin must not claim to protect every turn. Failure removes its contributions,
and later work may proceed without its interceptor. Pending interactions can
wait for an attached client; headless mode does not imply approval.

Use [`internal/plugin`](../../internal/plugin) and
[the lifecycle ADR](../adrs/0026-scope-plugin-processes-and-route-plugin-ui.md)
as authoritative references. Report missing capabilities explicitly; do not
fabricate methods or silently omit behavior.

## Validation and handoff

For each used capability, test initialization, command/tool execution, invalid
inputs, errors, cancellation, reload, cwd changes, and shutdown in isolation.
Test concurrent sessions if the plugin maintains state or performs side effects.
Inspect diagnostics and confirm valid protocol stdout.

Verify model/theme/diff behavior in the client, not merely preserved JSON keys.
Test MCP connectivity separately. Finish with changed files, backup locations,
verified behavior, unsupported features, and required user authentication or
installation steps. Parsing or launching successfully is not full compatibility.
