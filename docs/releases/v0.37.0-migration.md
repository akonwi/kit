# Migrating to Kit 0.37.0

Use the source and release artifacts at **tag v0.37.0** when following this guide. These instructions are for users and coding assistants; inspect the installed binary and running daemon before making changes. Do not copy credentials into prompts or commit them.

## From 0.36.x

1. Check the existing version and daemon before replacing anything:

   ```sh
   command -v kit
   kit version
   kit server status
   ```

   Allow active turns, subagents, and tool work to settle before restarting. Closing a client does not necessarily stop daemon-owned work. If you need a backup of native session data, take one while the daemon is stopped; do not edit Kit's SQLite files while it is running.

2. Upgrade via Homebrew (`brew update && brew upgrade akonwi/tap/kit`) once the formula is available, or manually extract the matching `kit_v0.37.0_<platform>.tar.gz` archive and put its single `kit` executable on PATH. Verify `command -v kit` resolves to the intended installation and `kit version` reports `0.37.0`. Do not assume replacing the executable also replaces an already running daemon.

3. Inspect the daemon with `kit server status`. Kit 0.36.2 speaks session protocol 39; Kit 0.37.0 speaks protocol 40. The 0.37.0 client will **not** automatically stop a protocol-39 daemon. If the old daemon is running, wait for work to settle and restart only when interruption is acceptable:

   ```sh
   kit server restart
   kit server status
   ```

   If no daemon is running, start Kit normally instead of restarting. Reopen any older clients with the new binary. If you are not ready to restart, keep using a matching older client for the older daemon and defer the upgrade. Do not point a downgraded daemon at native data that a newer release may have migrated.

4. Check an existing saved session, its transcript and direct-shell history, provider login, and any project MCP/plugin integrations that matter to your work. Native database migrations run at server startup; do not manually rewrite native or legacy databases. Compatible configuration and credentials are reused in place, but successful discovery alone does not prove a provider or MCP server works. Reauthenticate through supported login flows if needed.

Stable releases from 0.37.0 onward that retain protocol 40 can share a daemon across release labels. This promise does **not** cover 0.36.x, release candidates, independently built development worktrees, protocol changes, or database downgrade safety. The client reports unverified pairs without restarting the daemon. Use `kit server status` to distinguish binary version, daemon version, and protocol; only restart intentionally.

## Changed workflows

- **Images:** `show_image` displays a persisted image to the user but no longer adds image bytes to model context implicitly. Use `inspect_image` when the model must inspect an image. Recheck prompts, tools, and plugins that relied on the old `show_image` model-visible result. Do not assume general multimodal token accounting is complete.
- **Direct shell:** `!` and excluded `!!` executions are now retained in a dedicated session history and recalled from the composer. They are no longer projected as a synthetic bash-role transcript message. Included executions still enter model context as droid context boundaries; excluded executions do not.
- **Session deletion:** deleting a saved session permanently removes session-owned data and reserves its ID. It fails when owned work is active, and it does not erase content independently copied into another session. Check which session you selected before confirming deletion; do not use deletion as an upgrade step.
- **Reasoning controls:** effort-history updates apply only to supported public OpenAI GPT-6 standard Responses models. Do not infer this behavior for Codex, custom gateways, Anthropic, or arbitrary models. A policy-stop error is not automatically retried.

No manual configuration format conversion is prescribed for 0.36.x. Keep existing settings, prompts, skills, themes, and plugins unless you have identified a particular behavior to adjust. Preserve private credential files and use Kit's supported authentication commands rather than editing them by hand.

## From 0.35.x or earlier

First follow the [0.36.0 migration guide](v0.36.0-migration.md), then its [0.36.1](v0.36.1-migration.md) and [0.36.2](v0.36.2-migration.md) adjustments before applying the steps above. The native Go runtime does not import legacy sessions, databases, or credential internals. Do not delete legacy data merely to upgrade.
